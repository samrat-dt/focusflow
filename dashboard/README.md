# Focusflow dashboard

The dashboard for focusflow: a board of your work in five lanes (Next · In progress · Paused · Review · Done), a
Projects screen with expandable subtasks, an Archive, and an Inbox for talking to tasks and to each project's
coordinator. Everything it does goes through the `focusflow` CLI; see `JOURNEYS.md` for how the screens fit together.

- **Stages** are focusflow's own: backlog · next · in progress · paused · review · done. Whether a terminal is open
  (⌨) or a headless run is going (⚙) is a separate marker on the card.
- **Nothing opens a terminal by itself.** Start, Resume, Focus and "Open terminal" do, because you clicked them.
  Messages run headlessly. Pause, Send to review, Approve and Next only change status.
- **Projects** have one permanent coordinator session each: message a project and it decides whether the ask belongs
  to an existing subtask or needs a new one. Schedule a project to have it reviewed on a rhythm.
- Search (`/`), a stats strip, and a health chip (`focusflow doctor`) are always on screen.

## How it works

- focusflow owns the tasks. The dashboard reads focusflow (its JSON and, read-only, `focusflow.db`) and changes it only
  through the focusflow CLI.
- Every change is appended to an event log under `~/.focusflow/dashboard/data/events/`. That log is the truth;
  `~/.focusflow/dashboard/cache/store.db` is a disposable SQLite cache rebuilt from it at every start.
- The server binds to `127.0.0.1` only and checks a token, the Host header and the Origin header.
- All state lives under `~/.focusflow/dashboard/` (device id, token, tunables, event log, cache, log). `focusflow backup`
  covers it and `focusflow sync` can mirror it to a private git repo.

Requires macOS, Node 24+, and focusflow on your PATH (or `FOCUSFLOW_BIN`). No dependencies to install.

## Set up

From the repository root, `make install` installs focusflow and restarts the dashboard. To install the dashboard's login
item the first time:

```
make dashboard        # = cd dashboard && node bin/setup.js --launchd
```

Safe to run again. `focusflow dashboard` (or `npm run url -- --open` here) opens it with the token.
To run it by hand instead: `npm start`.

**Focusflow.app.** `make app` (or `npm run app`) builds `~/Applications/Focusflow.app` with its own window and an
always-on-top mini board (⇧⌘M). Opening it starts the dashboard if it is not running.

## If something goes wrong

The dashboard runs in the background and opens in your browser or in the app. Two things can go wrong. The steps below
are also on screen (the app shows them itself) and in setup's output.

### Chrome forgot the access token

The dashboard is running, but this Chrome does not have its access token, so it cannot show your tasks.

1. Open Terminal (press Command-Space, type Terminal, press Enter).
2. Copy this command, paste it into Terminal, and press Enter:

   ```
   cd <project folder> && npm run url -- --open
   ```

3. Chrome opens the dashboard and remembers the token. You will not need to do this again.

### Chrome says it can't connect

The dashboard is not running, so there is nothing to connect to.

1. Open Terminal (press Command-Space, type Terminal, press Enter).
2. Copy this command, paste it into Terminal, and press Enter:

   ```
   launchctl kickstart -k gui/$(id -u)/local.focusflow.dashboard
   ```

3. Reload 127.0.0.1:4177 in Chrome.

If Terminal says it could not find the service, the login item is not installed. Run this instead and leave that Terminal window open:

```
cd <project folder> && npm start
```

Easier: open "Focusflow.app" (in your Applications folder). In one click it starts the dashboard if it is not running, then opens it with the token. If macOS says it cannot verify the app, right-click it, choose Open, then choose Open again.

## Task chat and inbox

Open a task's drawer to see its thread and send a message. Replies are whatever the task's agent posts to your
focusflow queue (`focusflow message user …`).

- **Send is headless** when nothing is running: a fresh unattended run, or a continuation of the existing claude session
  (`claude --resume <id> -p …`). The first-ever headless send for a task asks you to confirm. If a terminal session is
  already open for the task, Send goes to that session's inbox instead, so two runs never share a session. "Queue only"
  leaves the message for the next Resume.
- **Sent → delivered → replied.** A queued message shows *sent* until the task's session has actually seen it
  (focusflow stamps `delivered_at` when a hook or an inbox listing surfaces it), then *delivered*.
- **Notifications:** an unread badge, the tab title, an optional sound, and a macOS banner via `osascript`.
- **Never consume your queue.** The dashboard only reads it. Anything else that pops the user queue makes messages
  arrive already read, so they will not notify.
- On the very first run the existing queue is imported as already read.

## Tunables (`~/.focusflow/dashboard/instance.json`)

`terminal_app`, `data_dir`, `cache_db`, and under `tunables`: `port` (4177), `tick_minutes` (5), `stale_days` (5),
`due_soon_days` (3), `inbox_poll_seconds` (5), `notifications` (true; false turns the macOS banner off),
`working_window_seconds` (15), `nudge_stall_seconds` (30).

The `claude` binary used for headless continuation is resolved from `PATH`; set `CLAUDE_BIN` to point at a specific one.

## Tests

`npm test` (built-in runner; no real `~/.focusflow` is touched).

## Remove

`node bin/setup.js --uninstall-launchd` removes the login item. State stays in `~/.focusflow/dashboard/`.
